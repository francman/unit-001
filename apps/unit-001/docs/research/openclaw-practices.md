# OpenClaw practices for Bob's autonomous mission runtime

Recommend three slices: **agreed mission formation**, **durable next-action scheduling**, then **bounded delegation with completion receipts**. These advance Bob's always-on mission rather than add another chat surface. Cost limits, stop semantics and observable outcomes are acceptance requirements for all three.

Reviewed 2026-11-09 against official OpenClaw main [`f947b3caf5d0fb04c780205dfeff509d87cd2527`](https://github.com/openclaw/openclaw/tree/f947b3caf5d0fb04c780205dfeff509d87cd2527). This source pin may contain unreleased work. Documentation and the named implementation/tests establish implemented patterns; this assessment did not run OpenClaw or measure its memory use. Effort and VPS cost below are engineering judgments, not measurements.

## Why the first-run experience must differ

OpenClaw's [bootstrapping guide](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/start/bootstrapping.md) and [BOOTSTRAP template](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/reference/templates/BOOTSTRAP.md) provide a short collaborative identity setup. The template explicitly allows ordinary requested work before that ritual, and considers edited identity files or a memory directory evidence of configuration. That does **not** establish mission approval. Its [bootstrap resolver](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/src/agents/bootstrap-mode.ts) also excludes nonprimary and cron runs from the ritual; copying it would leave headless elder-agent provisioning unsupported.

Bob should keep the short conversation but persist `awaiting_creator → drafting → awaiting_approval → agreed` through the sole owner. Approval binds creator principal, installation, mission ID and exact revision. A parent/organization adapter supplies authenticated delegated authority; model claims, remembered instructions, display names and channel text cannot create it. Ordinary authorized conversation may refine the draft; autonomous cycles require agreement. #14 already captures this distinction. Organization comparison remains #41, messaging transport #40 and browser research #39.

OpenClaw's [standing orders](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/automation/standing-orders.md) give a useful mission vocabulary: scope, trigger, approval and escalation. The prose is guidance, not an authorization mechanism. Bob's host must enforce the agreed limits and invalidate stale decisions when the revision changes.

## Implementation evidence and limits

- [Automation lifecycle](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/automation/cron-jobs/how-it-works.md): persisted jobs/results, deferred work, bounded recovery and unknown-delivery treatment. Its promotion workflow asks for the schedule/task in plain language and visibly tests the job after confirmation. Bob should require approved mission authority before promoting repeated work; repetition itself is not consent.
- [Goal control](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/tools/goal.md): revision-bound controls, idempotent receipts and continuation through existing admission. Crucial caveat: a saved active session goal alone does not start a process or schedule after shutdown. Bob needs its mission controller, not merely a copied goal prompt.
- [Subagent handoff](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/concepts/subagent-yield-handoff.md): one completion owner, stable child lineage, bounded findings and fresh admission rather than revived authority. This is a complex implementation; borrow invariants, not the subsystem wholesale.
- [Progress cards](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/tools/progress-card.md): parent-owned bounded saved progress, reconnect reads and revision-safe clearing. A card is a projection, not proof of external success or authorization.
- [Usage accumulation tests](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/src/agents/embedded-agent-runner/usage-accumulator.test.ts): actual assertions preserve zero versus unknown, cache buckets and mixed billed/estimated provenance across attempts. [Usage guide](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/concepts/usage-tracking.md) separates subscription quota and API estimates.
- [Fallback authority tests](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/src/agents/model-fallback.operator-model-policy.test.ts): denied models never prepare/execute and authority is checked again after asynchronous preparation. This is stronger than silently selecting another available model.
- [Session search](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/docs/concepts/session-search.md): bounded excerpts and anchored history. Its documented default can include other agents/users; Bob must preserve current isolation. Excerpts can contain credentials, so this is a deliberate evidence-sharing boundary.

## Fit and adoption boundary

These adaptations fit Bob's always-on mission goal and existing public-Durable architecture. Preserve the two tenets: no upstream Pi patches; measure response-path work and move slow projections/reconciliation into background tasks. Do not import OpenClaw's gateway, control UI, worker fleet, avatar generation or provider quota subsystems to deliver these slices. No RAM measurement here establishes that full OpenClaw, or new concurrent Bob children, fit the 512 MB VPS.

OpenClaw's pinned [license](https://github.com/openclaw/openclaw/blob/f947b3caf5d0fb04c780205dfeff509d87cd2527/LICENSE) is MIT. If substantial source or documentation is copied, retain its copyright/license notice and review component/dependency notices. This assessment recommends independent adaptation through Bob's existing APIs; it adds no dependency, grants no external messaging authority and does not approve implementation.

## Coding definition and delivery order

The three recommended slices are one mission mechanism, not three new runtimes. Existing anchors: app `Agent.open`/`submit`/`status`, owner IPC in `src/service.ts`, observed runtime facts in `src/orientation.ts`, and unit-memory's public Durable document/task integration. `src/missions/state.ts` already defines version-1 `unit.mission`, activation identity, bounded policy fields and a nonexecuting deadline-holder task. `Agent.open` does not install that foundation or run mission decisions. Reuse it; do not create a second mission document. #14 must approve the ownership decision: one installation mission belongs to its configured owner session; arbitrary conversation/session names do not create independent installation-wide authority.

Extend `src/missions/state.ts` and proposed `contract.ts` with tagged states: `awaiting_creator`, `drafting`, `awaiting_approval`, `agreed`, `paused`, `blocked`, `completed`. Every created mission carries ID/revision; drafts carry goal, scope, permitted registered operations, limits, success evidence and review cadence. Agreement adds the provisioned creator principal, policy revision and approval receipt. Keep process-running and mission-active separate. Propose `MissionDoc` version 2 with an explicit migration: preserve version-1 identity/objective/policy and reconcile its owned hold task; no existing record gains agreement or execution authority. A null prior document starts awaiting creator; an existing unapproved record becomes a recoverable pending draft. Preserve stopped/paused intent. Root-owned provisioning policy is not stored in model-writable memory. Add exact version-1 SQLite migration fixtures before changing this schema.

`src/missions/control.ts` proposes/revises/approves/pauses/resumes with an operation ID, exact expected revision and authenticated creator context. Reusing an operation ID with identical content returns its receipt; different content rejects. Approval publishes the exact agreed revision atomically. Revision or policy changes invalidate queued decisions; restart resumes the same handshake or agreed controller checkpoint. Creator expansion/handoff is a privileged policy change. A child receives scoped delegation identity and remaining limits, never the parent's full credential or a permission claimed in returned prose.

`src/missions/controller.ts` implements a public Durable task: inspect committed state → choose one bounded action → admit against the current agreement → execute → verify → record outcome → sleep or continue. Each occurrence/action has a stable ID. Unknown external outcomes enter reconciliation; do not retry a write merely because no reply arrived. Limits include elapsed time, action count, child concurrency and recorded spend/usage coverage. Host admission can enforce registered operation limits; retained generic coding tools can bypass narrow model/tool instrumentation, so neither shell-effect isolation nor a hard global billing cap may be claimed.

`src/missions/delegation.ts` stores child ID, parent decision, delegated revision/scope, accepted/working/terminal state, result evidence and parent-delivery receipt. Initially admit at most one child model execution concurrently on the 512 MB host; allow a second only after measured capacity. Parent continuation consumes recorded results once through existing owner admission. Parent stop retires outstanding continuation obligations and requests child cancellation; ambiguous child side effects remain reviewable.

Ordered vertical slices: #14 approve state/authority and concrete traces; #15 implement durable first-run agreement plus fake controller; #16 exercise startup/restart without terminal; #17 add owner controls and read-only TUI mission projection; #15 enable one deterministic mission action with sleep/reconciliation; #27 add bounded proposal children and parent selection. Each slice needs real SQLite restart/crash/replay tests, stale approval/revision and denied authority-expansion tests, and proof that paused/unagreed missions do not admit autonomous work. UI slices require actual 80×24/40×12 PTY inspection. Keep existing latency gates; measure wake cost and incremental RSS before target capacity claims.

Follow-on definitions: #26 owns a bounded saved progress projection and scoped evidence/history reads; #42 owns usage provenance and coverage before mission spend reporting; provider fallback remains deferred until safe replay boundaries are decided. Their source comparisons above inform those issue specifications, not an instruction to implement all seven features at once. No existing schema migration may silently enable autonomy or broaden trusted operators.

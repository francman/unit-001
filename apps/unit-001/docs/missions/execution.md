# Checkpointed bounded work

The execution engine can take several bounded steps from one agreed assignment. Each step uses a durable synthetic input, executes only approved tool names, and checks actual files before continuing. An assistant saying “done” cannot prove the work is complete. Completing this assignment does not complete the agent's enduring mission. The current schema still combines purpose and work terms; the [purpose and work contract](purpose.md) defines the required separation and continuous-planning gap.

The engine does not automatically start existing agreements. [Bounded-work controls](controls.md) provide protected activation and inspection. Native supervised-process qualification remains #16. The normal conversation and existing nonexecuting mission holder keep their behavior.

The first verifier accepts an exact criterion such as `sha256:EXPECTED_HEX_DIGEST:reports/result.txt`. The creator approves that literal requirement with the mission terms. Unsupported prose criteria or additional approval rules block before spending model tokens. This deliberately supports verifiable artifact work first; it does not interpret arbitrary goals as proof.

## Authority and limits

The owner rechecks the exact protected creator receipt before cycle admission, each provider attempt and each direct or nested tool call. Cycles, request attempts, no-progress steps, retry deadlines and wall-clock limits are durable. Waiting uses Durable sleeps and makes no model requests.

The decision and its effect are one step. Problem: a check that runs before the effect leaves a gap. Example: `remember` is admitted, a maintenance hold or pause commits, and the memory write then commits under the hold. Rule: every storage commit a mission action makes (memory writes included) re-reads the execution ledger, the maintenance hold, that its own intent is still pending, and the protected authority inside the same Durable transaction; if any check fails the commit is rolled back. The same holds for the provider reservation. Protected authority is a file outside storage, so it orders by time: a publication whose rename finished before that read closes the effect, and the owner's pause or stop is acknowledged only after its own ledger commit, which Durable orders after any effect already committing. A revocation published without an owner commit can still miss an effect whose transaction read the file just before the rename. File and shell effects (`write`, `edit`, `bash`) cannot join a transaction; for them the check runs at intent admission and a pause aborts the running call.

A tool-name grant retains that tool's service-account authority. In particular, `bash`, `write` and `edit` are broad capabilities; mission scope prose is not a filesystem or network sandbox. Developer-local authority is writable by the developer account and supplies no root attestation. Managed authority remains root-owned. Same-UID coding tools remain trusted, as in the existing installation security model.

Provider dispatch reserves an attempt before sending it. Mission requests disable provider SDK retries and abort at the mission deadline. With an estimated spend limit, the engine reserves a conservative full-context/output ceiling using the configured model's highest known rates. Unknown or zero pricing cannot admit a capped request. A settled error or unpriced response retains its reservation; a crash without a terminal receipt stays unknown and blocks further dispatch. Durable's own generation retry after a settled failure, including one whose backoff spans a restart, is a new attempt: it passes the same gates and counts against the request allowance. An attempt still in flight when the host stops stays unknown, and every later attempt, that retry included, is refused until reconciled. These are accounting estimates, not a provider billing cap. External shell/tool spending is outside that estimate.

Mission requests never become deferred. Durable polls a deferred handle later without the provider session, so the poll could not be attributed to the mission or pass its gates. A mission request therefore never asks for deferral, and a provider that defers anyway gets its handle cancelled; the attempt then ends as an unpriced error with its reservation kept, because the provider accepted the work. A handle stored by an earlier build before this rule cannot be attributed; closing that case needs Durable to pass the session to `fetchDeferred`.

Executable missions accept only the reviewed built-in action catalog. Spawn-capable extensions, image/classifier helpers and new tool implementations need their own admission design before becoming grantable. The current catalog makes no auxiliary provider requests; direct model access from an unreviewed extension is not covered by these gates.

## Persistence and interruption

`unit.mission.execution` is a separate version-two session document with an explicit version-one migration. It preserves the formation document and legacy task schema. One activation atomically creates one controller and its task-owned execution conversation. Every cycle saves its stable request ID and submission in the same commit. Reopening observes that submission rather than admitting another.

Tool intent is recorded before execution. Successful completion and known pre-dispatch rejections settle it. Failed or interrupted effects stay uncertain: the verifier may accept independently observable completion, otherwise the engine blocks rather than repeating an uncertain action. This includes an ordinary tool failure whose partial effects cannot be proved absent. After a restart, Durable may rerun a replay-safe tool from its saved intent without the first-dispatch hook. In the mission conversation each reviewed action first meets the current admission decision at execution (receipt and intent, maintenance, lifecycle, allowlist); a denied rerun does not run and its intent stays uncertain, because the interrupted attempt may have acted. An admitted rerun relies on that tool's own replay contract, such as idempotent memory receipts, and its commits are checked as above. No action starts beside an unresolved one: while another intent is pending and no call in this process is running it, a new call is refused before its intent and a rerun is refused as interrupted. Example: an unsafe `write` is interrupted; after restart the saved round's next call, fresh or rerun, does not run, and the engine blocks on the uncertain write. Ordinary conversations keep Durable's replay unchanged. An explicit controller abort closes mission intent before owned work finishes draining. Task termination alone is not mission success; the execution document and evidence are authoritative.

File observations reject escaping paths, symlinks, directories, changing files and files above 4 MiB. Each observation has a timestamp. It proves the observed content at that point, not that a separately running process can never change it afterward.

## Purpose runs

Continuous operation reuses this admission path with a different ledger: provider sessions and conversations of purpose runs are looked up in `unit.mission.purpose`, and each attempt settles by its own ID against the purpose's lifetime ledger. Purpose runs differ in three ways: the only action is `unit_work_write` for the run's declared path, a provider error or abort stays reserved instead of settling as unpriced, and the protected read happens inside the commit for every step, including the tool's fence commit before its file write. See the [purpose contract](purpose.md#continuous-operation-slice-2).

## Local evidence and remaining work

Focused faux-provider tests use real SQLite and the real coding write tool. They cover two autonomous verified steps, false completion, finite cycles and requests, receipt revocation, maintenance sleeps across reopen, interrupted request recovery, a scheduled provider retry across reopen, recovered tool reruns under revoked and current authority, a hold, pause or revocation landing between a fresh or recovered action's admission and its storage commit, saved sibling actions beside an interrupted one, requested and provider-imposed deferral, an ordinary-chat rerun beside a bound mission, pause during dispatch, racing activation, explicit abort and verifier boundaries. No paid provider calls are used.

Protected, revision-bound execution intent and owner controls are implemented; ordinary operator messages cannot start work. Real process-kill, persisted-wakeup and single-owner fixtures pass, while native systemd installation/update/rollback qualification remains #16. Research/ticket delivery remains #27. Continuous purpose-driven planning requires the separate purpose/work model above. New verifiers need explicit host semantics and tests; model judgment does not silently become verification.

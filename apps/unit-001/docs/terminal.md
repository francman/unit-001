# Terminal interface for the always-on agent

Run `agent` over SSH, or `bob` for an installation named Bob, after an administrator has granted [operator access](operations.md#operator-access-and-sudo). Bare interactive entry opens the terminal client of the running owner; it does not read provider credentials, open SQLite or create a second model runtime. `attach` remains an explicit equivalent. If the service is unavailable, a persistent screen shows the setup/start commands and waits for you to exit; it never starts the service automatically.

Source development uses the same rich interface around its already-open foreground owner. Explicit foreground options such as `--model` and `--session` retain their existing owner behavior. Closing a foreground session closes that process; closing an attached client leaves the managed service running. The header and footer distinguish these modes.

## Rich interface

The full-screen interface has a branded name/session/model header, a scrolling Markdown conversation, compact tool outcomes, and a fixed composer. An empty workspace explains where to ask a question or describe a task. Live updates leave the draft and cursor intact. Output follows the conversation until you scroll away to inspect earlier text.

The composer border names the agent and shows the newline shortcut; ordinary typing appears immediately. Tool outcomes use compact `[status] name` rows. Actionable failures are marked **Error** even in monochrome. The header keeps the model and version visible; `/status` provides the process ID.

- **Enter** submits; **Ctrl+J** or **Shift+Enter** inserts a newline. The footer shows the active shortcuts.
- **PageUp/PageDown** scroll; **Ctrl+Shift+F** searches the displayed transcript when the terminal forwards that key combination distinctly. In search, **Enter/Shift+Enter** moves between matches and **Esc** closes search. These are default bindings; this does not search older or other sessions' history.
- `/status` shows identity, session, PID, version and activity, then fresh owner-process start time, uptime and observation time; `/help` lists commands.
- `/memory` shows counts; `recall QUERY` finds evidence, `remember TEXT` stores a statement, `forget ID` asks for confirmation, and `sleep` schedules consolidation. See [memory commands](memory.md). These operations never submit a model request.
- `/cancel`, or **Ctrl+C** while working/submitting, cancels all work in the chat, not only your latest send: the current run, its tools and every queued input, including other attached operators' inputs. The footer labels it **cancel chat**. It cannot be limited to one run, because Durable has no public operation that checks which run is active and aborts only that run in one step, and a check followed by a separate abort could stop a later run instead.
- `/exit`, `/detach`, **Ctrl+D**, EOF or a lost SSH connection detaches without cancelling admitted work. Idle **Ctrl+C** also detaches. An unsent draft is saved for the next attach (see below).

### Draft recovery

The rich interface keeps one unsent draft per installation and session in the invoking OS user's data directory, under `drafts/` (`~/Library/Application Support/unit-001/drafts` on macOS, `$XDG_DATA_HOME/unit-001/drafts` elsewhere, or under `UNIT_001_HOME`). It is client-side only; the owner is not involved.

- Edits are written at most about once a second, and always on exit (normal exit, fatal disconnect, SIGHUP/SIGTERM). A killed or dropped client can lose the last second of typing. If a write fails, the terminal prints `Draft not saved: REASON` on exit.
- The next attach to the same installation and session puts the draft back in the editor with a one-line notice. It is never sent without you pressing Enter, and keys typed in the first 200 ms after a restore (type-ahead meant for the previous prompt) are dropped, then Enter is ignored for another 300 ms, so a stray keypress cannot send text you have not seen. The type-ahead is dropped by the interface, not by draining the terminal, so the keyboard protocol the terminal negotiated at start (Kitty or modifyOtherKeys, which the search and newline shortcuts need) stays active. A file recorded for another installation or session, a file older than 7 days or dated more than 5 minutes in the future, or text over 16 KiB is ignored.
- The file is `0600` in a `0700` directory, replaced atomically. Anyone who can read your files can read the draft, so do not rely on it for secrets.
- The drafts directory and file are checked before use. The directory must be a real directory (not a symbolic link), owned by you, with no group or other access; the file must be a regular file you own, at most 128 KiB, opened without following a symbolic link. Otherwise nothing is read, the terminal says `Saved draft not restored: REASON`, and the exit message reports the draft as not saved. A directory the client creates is set to `0700` through its opened descriptor; an existing one, including one another process created first, is never changed. The path above it is walked as the kernel resolves it, following every symbolic link wherever it sits: each entry on the way, links included, must be owned by you or root, and each directory must be writable by nobody else unless it is sticky (as `/tmp` is). Otherwise another user could swap a path component, or a link they own, between the checks and the writes, so the store refuses the location.
- Restored text has terminal escape sequences and control characters (other than newline and tab) removed, and the same is done before saving, so a planted file cannot change your terminal. An unconfirmed send whose text sanitizes to nothing (a prompt of format characters such as U+200B only) keeps its request ID and digest; the restore notice says its text is not shown.
- On every attach the client deletes draft files and leftover `.draft-*.tmp` files in the directory that are older than 7 days, including those of sessions or installations you no longer use.
- Drafts are not kept on the managed administrator path (`sudo <name>`): that client runs as the service account, so its draft would sit in the installation's own state, where the agent's tools can read it. The terminal shows `Copy draft before exit; it is not saved.` there. Operator clients and remote clients keep drafts in their own user's directory.
- When you submit, the client writes the text, its request ID and a digest (SHA-256) of the prompt as sent to disk, and waits for that write, before the request leaves. A client that crashes right after sending therefore still finds the ID on the next attach. If that write fails (for example the drafts directory fails its checks), the send is held: nothing leaves the client, the text returns to the editor, the file keeps what it held before, and the notice names the reason. A held retry changes nothing else either: if it resends a send whose reply was lost, that send stays unconfirmed under its ID, in the file once storage recovers, so a reopen still checks and reuses that ID. Pressing Enter again on the same text sends it under the same ID without saving it; the ID is then only on screen and in the exit message, so a crash before the answer loses it. Without this choice, a broken drafts directory would make sending impossible from this terminal. This choice is not offered when the file holds an earlier send under another ID whose outcome is unknown (a lost reply, or a restored send the owner has no record of), because the unsaved send would replace it there; send that text again, or fix the drafts directory, first. The send stays in the file until the owner answers. If you typed something new before exiting, the file keeps both: the editor gets the new text and the earlier unconfirmed send is shown below the conversation until you send again. Once the owner answers (including an unanswered-with-reason reply), the unconfirmed text is removed from the file; your newer typing stays.
- If the client exits before the answer, the next attach restores the send and asks the owner, once, whether it was admitted (see [send admission lookup](#send-admission-lookup)). The answer replaces the restore notice:
  - **Received with this exact text** (queued, placed in the conversation, answered, or ended without an answer and its reason): the send is removed from the file, and from the editor if you have not changed it. Nothing is sent. "Placed" means the input is in the conversation and owned by a run; an owner started inhibited places work without running it.
  - **Received, text not confirmed** (the owner has no receipt for the ID, or the saved send has no digest): the ID is settled, but the text stays, in the editor or below it, because the owner cannot show that it received this text. Sending it again starts a new request.
  - **No record as of now**: the text and its ID stay in the file, whatever you then type or undo, until the owner settles it or you send something. Sending exactly the same text again reuses its request ID, so the owner admits it at most once even if the first send is still in transit.
  - **Belongs to a different prompt** or another operation: the text was not sent under that ID; sending it again uses a new ID.
  - **Could not check** (owner unreachable): the text stays, and sending the same text again still reuses its ID.
- Sending a prompt whose digest equals an unconfirmed send's (restored, refused, or one whose reply was lost in this session) reuses that send's request ID. The digest decides, not the saved text: the file holds sanitized text, which can differ from what was sent, and an ID reused for different text would be refused. Edited text, and a saved send without a digest, get a new ID.
- If the owner answers the send with an error, the client does not assume a refusal: an error can follow the admission (the owner replaces a reply over 1 MiB with an error). It asks the owner about the ID first. Admitted with this exact text: the send is settled and the error is shown. Admitted but unverified (the owner keeps no receipt for the ID, so it cannot show it received this text): the ID is settled, and the text comes back as below; sending it again starts a new request. No record (for example a maintenance hold) or another prompt: the text returns to the editor if it is empty, otherwise it is kept in the file as the earlier send; with no record, sending the same text again reuses its ID. If the owner cannot be asked, the send stays unconfirmed with its ID. Only the latest attempt under an ID counts: if the same text sent again under it is answered, it is not given back.
- Two terminals of the same user on the same installation and session share one slot: the last writer wins, and a confirmed send from one clears the other's unconfirmed text. Both can restore the same draft; because both reuse its request ID for the same text, the owner still admits it once.
- The file holds one unconfirmed send. Sending new text while an earlier send is unresolved replaces it in the file; the terminal prints every unresolved request ID on exit.

Those detach semantics apply to a managed service client. In foreground mode, **Ctrl+D** and idle **Ctrl+C** are labeled **exit**; the caller closes the foreground owner after the view exits. Unfinished durable work can resume on the next launch. Busy **Ctrl+C** still requests cancellation.

One client allows one unresolved submission at a time; another prompt stays in the rich editor when rejected. Inputs are limited to 16 KiB. Routine submission notices are compact; uncertain send failures include a request ID. The plain client also asks the owner about a send answered with an error and says what it found: admitted, admitted without confirming this prompt (resend only under a new ID), another prompt or operation, or no record as of now (the request may still arrive, so retry only with the same ID). Retry with `agent send --request-id ID "the same prompt"` to avoid duplicate admission; the owner refuses the same ID with a different prompt. Reattach manually after a disconnect or service restart.

### Send admission lookup

The owner answers, for one request ID in the main chat, whether a send was admitted. The answer comes only from committed state: the lookup never sends the prompt, waits for the answer, or starts scheduled work, and it works during a maintenance hold or inhibited startup. It is a separate owner operation (`admission`), available to operators; the browser does not offer it.

- **Admitted**, with its source (model or host facts), its outcome (queued, placed, answered, or unanswered with a reason of at most 200 characters) and how its prompt is known: **exact** (matches the digest the client sent), **recorded** (a receipt exists; no digest was sent) or **unverified** (no receipt, see below).
- **Rejected**: the ID belongs to a different prompt or to another kind of operation, so this prompt was never admitted under it.
- **Not found**: nothing is committed under the ID as of the read. This is not proof that the send will never be admitted: a request still in transit (a slow SSH tunnel, an owner still processing it) can commit afterwards. Sending the same prompt under the same ID is the safe way to settle it.

Each new send with a request ID stores a receipt in the same transaction as its admission: the SHA-256 of the full prompt (over its UTF-16 code units, so prompts that differ only in unpaired surrogates digest differently) and the Durable submission ID. A later send with the same ID and a different prompt is refused instead of being answered with the first prompt's reply. Host-fact answers keep their full input, so they bind the same way without a receipt. The main chat keeps the newest 256 receipts; an older one is evicted, and its send, like any send admitted before receipts existed, is reported **unverified**: admitted, but its text cannot be compared. Any send under such an ID is refused ("can no longer be compared"), even with the same text: the remaining record holds only the first 2,000 code points, which cannot tell two prompts apart, and answering could return another prompt's reply. Look the ID up instead, or use a new ID. Receipts start empty in a forked chat.

## Status and bounded views

The footer shows recorded conversation-model token totals and estimated USD when the ledger has usable cost values. **Cost unknown** means the ledger cannot establish pricing; it never means a free request. Estimates are not provider invoices or subscription charges. Totals exclude tool and subagent usage; missing metadata remains unknown.

At 40 columns, the footer prioritizes **Enter send**, compact token totals, cost availability and cancel/detach controls. The composer border retains the newline hint. Ctrl+C is labeled **exit** while idle and **cancel chat** while working or submitting.

Tool cards retain recent committed successes/failures. A neutral `done` has no known outcome. A failed card adds a fixed summary line chosen from a host-classified code (for example `Exited with code 2.`), and the frame carries why a request failed and any waiting provider retry as typed values, so every attached terminal shows the same state. Frames never carry tool output or provider error text. Arguments, output and diffs are not in these cards or in watch frames: `/evidence [CALL_ID]` fetches one call's bounded, redacted evidence on explicit request. See [tool evidence](tool-evidence.md) for the retention and secret boundary.

Views contain at most 20 recent durable entries, 4,096 characters per displayed entry, 8,192 live characters and 32 tool status records. Truncation is visible. These are bounded snapshots: intermediate progress can fold together, and this is not a complete transcript export.

## Basic terminals and scripts

Use `agent attach --plain` for the basic line interface. It is also selected when `TERM` is missing or `dumb`, or the initial terminal is smaller than 40 columns or 12 rows. Plain mode submits one line at a time; while a draft is being edited, remote display updates wait. Execution continues. Partial answer text appears when its line or answer completes.

Attach requires an interactive terminal in either mode. Use `send` for scripts and pipes; its final-answer stdout contract is unchanged.

Set `NO_COLOR` in the attaching process for monochrome rich output: `NO_COLOR=1 agent attach`.

## Remaining gaps

The [design](terminal-design.md), [omp assessment](terminal-assessment-omp.md) and [other terminal assessments](terminal-assessment-others.md) explain the direction. Cross-session/older-history search, in-interface model/session switching, complete tool output beyond the evidence bounds and complete transcript export remain later work. The CLI does not yet load a user keybinding file; override support currently exists only through the TUI's programmatic API. Foreground source chat remains a separate owner, rendered through the same rich view and bounded projection.
